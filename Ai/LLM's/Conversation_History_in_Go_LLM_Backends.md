# Conversation History in Go LLM Backends

## Introduction

When building a chat application, users expect the AI to remember earlier messages:

```text
User: My name is Charan.
Assistant: Nice to meet you, Charan!

User: What is my name?
Assistant: Your name is Charan.
```

Most LLM APIs do not automatically remember previous API calls. Your backend must store the conversation and send the relevant history again with every request.

The central rule is:

> An LLM can respond using only the information included in its current context.

## 1. Why an LLM Forgets

Most LLM APIs are stateless. If the backend first sends:

```text
My name is Charan.
```

and later sends only:

```text
What is my name?
```

the model cannot know the answer. The second API request is independent of the first one.

To make the model remember, the backend sends the relevant history:

```text
User: My name is Charan.
Assistant: Nice to meet you, Charan!
User: What is my name?
```

This list of earlier messages is called **conversation history**.

## 2. Message Roles

A message normally contains a role and some content:

```go
type Message struct {
	Role    string `json:"role"`
	Content string `json:"content"`
}
```

| Role | Purpose |
|---|---|
| `system` | Instructions controlling the assistant's behavior |
| `user` | A message written by the user |
| `assistant` | An earlier response generated by the model |
| `tool` | Data returned by an external tool or function |

Example:

```go
messages := []Message{
	{Role: "system", Content: "You are a helpful Go programming teacher."},
	{Role: "user", Content: "What is a goroutine?"},
	{Role: "assistant", Content: "A goroutine is a lightweight concurrent function in Go."},
	{Role: "user", Content: "Show me an example."},
}
```

The final question is unclear by itself. Because earlier messages are included, the model understands that the user wants a goroutine example.

## 3. Request Flow

When a user sends a new message, the backend should:

1. Receive the message.
2. Identify the conversation and authenticated user.
3. Load relevant previous messages.
4. Add the new user message.
5. Send the assembled context to the LLM.
6. Receive the assistant response.
7. Save the assistant response.
8. Return it to the client.

```text
Client -> Go Backend -> Database: Load history
Go Backend -> LLM API: History + new message
LLM API -> Go Backend: Generated answer
Go Backend -> Database: Save messages
Go Backend -> Client: Return answer
```

The Go backend—not the model—is responsible for assembling the conversation.

## 4. Basic Data Structures

```go
package chat

import "time"

type Conversation struct {
	ID        string
	UserID    string
	Title     string
	CreatedAt time.Time
}

type Message struct {
	ID             string
	ConversationID string
	Role           string
	Content        string
	CreatedAt      time.Time
}
```

A conversation groups related messages. Different chats should have different IDs:

```text
conv-123 -> Go discussion
conv-456 -> Docker discussion
```

This prevents unrelated messages from being mixed together.

## 5. Simple In-Memory Go Implementation

This first version stores messages in memory so the main idea is easy to see.

```go
package chat

import (
	"context"
	"fmt"
	"sync"
)

type Message struct {
	Role    string `json:"role"`
	Content string `json:"content"`
}

type LLMClient interface {
	Generate(ctx context.Context, messages []Message) (string, error)
}

type ChatService struct {
	llm           LLMClient
	mu            sync.Mutex
	conversations map[string][]Message
}

func NewChatService(llm LLMClient) *ChatService {
	return &ChatService{
		llm:           llm,
		conversations: make(map[string][]Message),
	}
}

func (s *ChatService) SendMessage(
	ctx context.Context,
	conversationID string,
	userInput string,
) (string, error) {
	s.mu.Lock()
	defer s.mu.Unlock()

	history := s.conversations[conversationID]

	if len(history) == 0 {
		history = append(history, Message{
			Role:    "system",
			Content: "You are a helpful Go programming teacher.",
		})
	}

	history = append(history, Message{
		Role:    "user",
		Content: userInput,
	})

	answer, err := s.llm.Generate(ctx, history)
	if err != nil {
		return "", fmt.Errorf("generate LLM response: %w", err)
	}

	history = append(history, Message{
		Role:    "assistant",
		Content: answer,
	})

	s.conversations[conversationID] = history
	return answer, nil
}
```

The important call is:

```go
answer, err := s.llm.Generate(ctx, history)
```

The backend sends the relevant history, not only the latest user message.

The mutex prevents unsafe simultaneous access to the Go map. It is useful for this learning example, but a database and a better per-conversation concurrency design should be used in production.

## 6. How History Changes

For the first request:

```go
service.SendMessage(ctx, "conv-123", "My name is Charan.")
```

the model receives:

```go
[]Message{
	{Role: "system", Content: "You are a helpful Go programming teacher."},
	{Role: "user", Content: "My name is Charan."},
}
```

If the model replies with `Nice to meet you, Charan!`, that response is saved. For the next request:

```go
service.SendMessage(ctx, "conv-123", "What is my name?")
```

the model receives:

```go
[]Message{
	{Role: "system", Content: "You are a helpful Go programming teacher."},
	{Role: "user", Content: "My name is Charan."},
	{Role: "assistant", Content: "Nice to meet you, Charan!"},
	{Role: "user", Content: "What is my name?"},
}
```

The answer is possible because the name exists in the supplied context.

## 7. HTTP Handler

```go
type ChatRequest struct {
	ConversationID string `json:"conversation_id"`
	Message        string `json:"message"`
}

type ChatResponse struct {
	Answer string `json:"answer"`
}

type ChatHandler struct {
	service *ChatService
}

func (h *ChatHandler) SendMessage(w http.ResponseWriter, r *http.Request) {
	var request ChatRequest

	if err := json.NewDecoder(r.Body).Decode(&request); err != nil {
		http.Error(w, "invalid request body", http.StatusBadRequest)
		return
	}

	if request.ConversationID == "" || request.Message == "" {
		http.Error(w, "conversation_id and message are required", http.StatusBadRequest)
		return
	}

	ctx, cancel := context.WithTimeout(r.Context(), 30*time.Second)
	defer cancel()

	answer, err := h.service.SendMessage(
		ctx,
		request.ConversationID,
		request.Message,
	)
	if err != nil {
		http.Error(w, "failed to generate response", http.StatusBadGateway)
		return
	}

	w.Header().Set("Content-Type", "application/json")
	json.NewEncoder(w).Encode(ChatResponse{Answer: answer})
}
```

Example request:

```json
{
  "conversation_id": "conv-123",
  "message": "What is a goroutine?"
}
```

## 8. Keep Provider Code Separate

Use an interface so the chat logic is independent of Gemini, OpenAI, Claude, or another provider:

```go
type LLMClient interface {
	Generate(ctx context.Context, messages []Message) (string, error)
}
```

A provider implementation converts the application's messages into the provider's expected format:

```go
type GeminiClient struct {
	apiKey string
}

func (c *GeminiClient) Generate(
	ctx context.Context,
	messages []Message,
) (string, error) {
	// Convert messages to Gemini's request format.
	// Call the Gemini API using ctx.
	// Extract and return the generated text.
	return "generated response", nil
}
```

The resulting dependency flow is:

```text
HTTP Handler -> Chat Service -> LLMClient -> Provider API
```

This keeps provider-specific details out of the business logic and makes testing easier.

## 9. Store History in a Database

An in-memory map loses data when the server restarts and does not work cleanly across multiple server instances. A production service should normally use a database.

```sql
CREATE TABLE conversations (
    id UUID PRIMARY KEY,
    user_id UUID NOT NULL,
    title TEXT,
    summary TEXT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE TABLE messages (
    id UUID PRIMARY KEY,
    conversation_id UUID NOT NULL REFERENCES conversations(id),
    role VARCHAR(20) NOT NULL,
    content TEXT NOT NULL,
    request_id TEXT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

Messages must be loaded in their original order:

```sql
SELECT role, content
FROM messages
WHERE conversation_id = $1
ORDER BY created_at ASC, id ASC;
```

Define a repository interface:

```go
type MessageRepository interface {
	FindByConversationID(
		ctx context.Context,
		conversationID string,
	) ([]Message, error)

	Create(ctx context.Context, message Message) error
}
```

The service then coordinates the database and LLM client:

```go
type ChatService struct {
	llm        LLMClient
	repository MessageRepository
}
```

## 10. Context Windows and Tokens

You cannot send unlimited history. Every model has a context-window limit, which includes:

- System instructions
- Earlier user messages
- Earlier assistant responses
- Tool results
- The latest user message
- Space required for the new answer

Longer input generally means more tokens, cost, latency, and irrelevant context. It can also exceed the model's limit.

## 11. Managing Long Conversations

### Keep only recent messages

```go
func keepRecentMessages(messages []Message, limit int) []Message {
	if len(messages) <= limit {
		return messages
	}
	return messages[len(messages)-limit:]
}
```

This is easy, but it may remove an old important fact.

### Preserve system instructions

Do not accidentally remove the system message while trimming:

```go
func buildContext(messages []Message, recentLimit int) []Message {
	var systemMessages []Message
	var conversationMessages []Message

	for _, message := range messages {
		if message.Role == "system" {
			systemMessages = append(systemMessages, message)
		} else {
			conversationMessages = append(conversationMessages, message)
		}
	}

	if len(conversationMessages) > recentLimit {
		conversationMessages = conversationMessages[len(conversationMessages)-recentLimit:]
	}

	result := make([]Message, 0, len(systemMessages)+len(conversationMessages))
	result = append(result, systemMessages...)
	result = append(result, conversationMessages...)
	return result
}
```

### Summarize old messages

A stronger approach sends:

```text
System instruction
+ Summary of older conversation
+ Recent messages
+ Latest user message
```

Example summary:

```text
The user's name is Charan. He is learning Go backend development.
He previously asked about goroutines and channels. He prefers
beginner-friendly explanations with examples.
```

```go
func buildMessages(
	systemPrompt string,
	summary string,
	recentMessages []Message,
	newUserMessage Message,
) []Message {
	messages := []Message{{Role: "system", Content: systemPrompt}}

	if summary != "" {
		messages = append(messages, Message{
			Role:    "system",
			Content: "Summary of the earlier conversation:\n" + summary,
		})
	}

	messages = append(messages, recentMessages...)
	messages = append(messages, newUserMessage)
	return messages
}
```

In a production system, trimming should ideally use token counts rather than only message counts because message sizes vary.

## 12. Conversation History vs Permanent Memory

**Conversation history** belongs to one chat:

```text
User asked about goroutines.
Assistant explained them.
User requested an example.
```

**User memory or preferences** may be useful across chats:

```text
Name: Charan
Preferred language: Go
Explanation style: Simple and example-based
```

Do not automatically treat every message as permanent memory. Keep these concepts separate, for example with `conversations`, `messages`, and `user_preferences` tables.

## 13. Production Considerations

### Verify ownership

Never authorize access using only a conversation ID. Verify the authenticated user too:

```sql
SELECT *
FROM conversations
WHERE id = $1 AND user_id = $2;
```

### Do not trust roles from the client

The client should send text, while the server assigns `Role: "user"`. System messages must remain server-controlled.

### Use cancellation and timeouts

Pass `r.Context()` into the service and provider client. Add an appropriate timeout so abandoned or stuck requests can stop.

### Prevent duplicates

Clients may retry after a network failure. Accept a `request_id` and enforce uniqueness per conversation:

```sql
CREATE UNIQUE INDEX unique_message_request
ON messages(conversation_id, request_id)
WHERE request_id IS NOT NULL;
```

### Preserve message ordering

Two quick requests can load the same old history and generate out of order. Start by allowing only one active generation per conversation. More advanced services can use queues, sequence numbers, or per-conversation locks.

### Protect sensitive data

Chats may contain personal data, source code, or accidentally pasted secrets. Use authentication, authorization, TLS, retention rules, and careful logging. Prefer logging metadata instead of complete prompts:

```go
logger.Info(
	"LLM request",
	"conversation_id", conversationID,
	"message_count", len(messages),
)
```

## 14. Recommended Architecture

```text
HTTP Handler
    |
    v
Chat Service
    |--------------------|
    v                    v
Message Repository     LLM Client
    |                    |
    v                    v
PostgreSQL          Gemini/OpenAI/etc.
```

- **Handler:** decode and validate input, read authentication, invoke the service, and return HTTP responses.
- **Chat service:** verify access, load history, build context, call the model, and save messages.
- **Repository:** read and write ordered conversation data.
- **LLM client:** translate internal messages, call the provider, and normalize responses and errors.

## 15. Suggested Implementation Order

1. Store messages in an in-memory map.
2. Send complete history with each LLM request.
3. Move conversations and messages to PostgreSQL.
4. Verify conversation ownership.
5. Send only recent messages.
6. Add token-aware context trimming.
7. Summarize older history.
8. Handle retries, duplicate requests, concurrency, and partial failures.

Start with the fundamental flow before adding vector databases or sophisticated memory systems. The backend creates the model's usable context by combining system instructions, relevant conversation history, optional summaries or retrieved information, and the latest user message.
